# Мини-Evernote

Реализованы первые два спринта **US-01–US-10**. Можно создавать и редактировать заметки с автосохранением и чек-листами, группировать их по блокнотам и тегам, искать, перемещать в корзину и восстанавливать. Критерии приведены в [docs/requirements.md](docs/requirements.md).

## Запуск в Docker

Требуются Docker Desktop с Linux containers и Docker Compose v2. Локальная установка Node.js и .NET для этого запуска не нужна.

Из корня репозитория:

```sh
docker compose up --build -d --wait
```

| Адрес | Назначение |
| --- | --- |
| http://localhost:3000 | React-приложение |
| http://localhost:5080/swagger | Swagger UI |
| http://localhost:5080/openapi/v1.json | OpenAPI |
| http://localhost:5080/health | Проверка API и соединения с БД |
| localhost:5432 (по умолчанию) | PostgreSQL 18, база `mininote`, пользователь `mininote` |

Порты и параметры PostgreSQL при необходимости задаются в `.env` по образцу `.env.example`. Они опубликованы только на loopback-интерфейсе. Локальный пароль по умолчанию — `mininote-local-password`. Backend внутри сети Compose подключается к `postgres:5432`; с компьютера БД доступна на `localhost:5432`. Изменение порта `POSTGRES_PORT` не меняет внутренний порт БД.

В подготовленном рабочем каталоге локальный `.env` задаёт `POSTGRES_PORT=15432`, поскольку Windows запретила публикацию портов 5432 и 5433. Здесь подключение с компьютера: **localhost:15432**. Для запуска Backend без контейнера с этим портом задайте `ConnectionStrings__Notes=Host=localhost;Port=15432;Database=mininote;Username=mininote;Password=mininote-local-password`.

```sh
docker compose logs -f
docker compose down
```

PostgreSQL 18 хранит данные в Docker volume `mininote_postgres-data`, смонтированном в `/var/lib/postgresql`. Остановка, пересоздание контейнеров и повторная сборка сохраняют записи. `docker compose down -v` удалит volume вместе с данными. Миграции EF Core применяются автоматически при старте Backend; блокнот «Личное» создаётся миграцией. Backend ожидает успешного healthcheck PostgreSQL.

Параметры `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` используются при инициализации пустого volume. Для существующей БД изменение этих переменных само по себе не меняет пользователя и пароль.

## Что реализовано

1. Нажать «Новая заметка». Запись создаётся в выбранном блокноте, а из общего списка — в «Личном». Пустой заголовок получает имя «Без названия». Если имя занято в блокноте, сервер добавляет свободный номер, например «Без названия (2)».
2. Выбрать карточку, чтобы открыть заголовок, полный текст и чек-лист. Пустой список содержит сообщение и кнопку создания. Сохранённые записи доступны после повторного открытия приложения.
3. Нажать на заголовок или обычный текст заметки и начать печатать. Чекбоксы остаются на виду во время редактирования. Через 1 секунду после последнего ввода отправляются последние изменения. Статус «Сохранено» появляется только после подтверждения сервера; карточка обновляется, данные доступны после перезагрузки. Другие заметки не изменяются.
4. «Вставить чекбокс» добавляет задачу в текст заметки. Галочку можно поставить или снять, а по нажатию на подпись можно изменить текст. Чтобы удалить пункт, очистите строку и нажмите Enter или уйдите с поля. Изменения сохраняются автоматически. При обновлении базы прежние пункты добавляются в конец текста заметки с сохранением порядка и отметок.

При ошибке сохранения ввод остаётся в редакторе, видны сообщение и кнопка «Повторить сохранение». Ввод во время запроса не теряется; после ответа отправляются оставшиеся изменения. Если версия заметки уже изменилась в другой вкладке, редактор показывает конфликт, оставляет черновик на экране и предлагает явно отбросить его и загрузить сохранённую версию. Повтор создания использует тот же ключ и не создаёт дубликат.

При переходе к другой заметке или создании новой изменения отправляются сразу, без ожидания секунды. Если сохранение не удалось, переход блокируется; диалог предлагает «Повторить и перейти», «Не сохранять», «Остаться». При ошибке открытия записи можно повторить загрузку. Быстрый выбор другой карточки отменяет предыдущую загрузку.

### Организация заметок

- В боковой панели можно создать и выбрать блокнот. Чтобы перенести заметку, перетащите её карточку на нужный блокнот. С клавиатуры откройте заметку, нажмите «Перенести в блокнот» и выберите блокнот в боковой панели. При совпадении заголовков перенос добавляет свободный номер.
- В редакторе можно ввести новый тег или выбрать существующий из подсказок. Варианты написания без учёта регистра используют один тег. Кнопка рядом с тегом снимает его с заметки.
- Поиск находит часть заголовка или текста без учёта регистра, включая пункты чек-листа. Он одновременно учитывает выбранные блокнот и тег. Очистка поля сбрасывает поиск.
- «В корзину» убирает заметку из рабочего списка, поиска и фильтров. Заметку из корзины можно прочитать или восстановить в исходный блокнот со всеми тегами и отметками. Заголовок остаётся за заметкой на время её нахождения в корзине.
- Перенос, смена тегов и удаление ждут подтверждения сохранения черновика.

Один пользователь, без регистрации; сохранение требует доступного сервера. Заголовок может содержать до 200 символов, а текст вместе с задачами — до 2 610 000 кодовых единиц UTF-16.

## Два проекта

```text
frontend/                          React 19 + TypeScript + Vite
  src/api/                         типизированный HTTP-клиент
  src/components/                  общие компоненты
  src/features/notes/              компоненты списка/редактора и хуки их состояния
  src/utils/                       форматирование и сообщения ошибок
  src/App.tsx                      компоновка рабочего пространства
  tests/                           Playwright: UI и интеграция с API
  nginx.conf                       раздача SPA, reverse proxy к API
backend/                           ASP.NET Core, .NET 10
  Domain/                          Note, Notebook, Tag и правила изменения
  Application/                     заметки и чек-листы, DTO и абстракции
  Infrastructure/                  EF Core, Npgsql/PostgreSQL, репозиторий, миграции
  Api/                             REST-контроллеры, обработка ошибок
  Program.cs                       composition root
docker-compose.yaml                frontend, backend, postgres и постоянный volume
```

Backend — один `.csproj` с разделением на папки и пространства имён по слоям чистой архитектуры. Domain не использует EF Core и ASP.NET; Application зависит от Domain и абстракции репозитория; Infrastructure реализует её; API вызывает сервис приложения. Границы слоёв логические, отдельными сборками не закреплены. Будущие сущности остальных User Story не добавлены.

Frontend работает с API через Nginx на том же origin, поэтому CORS для контейнерного запуска не нужен. Runtime-контейнеры приложения работают от непривилегированных пользователей. Healthcheck Frontend проверяет цепочку Nginx → API → PostgreSQL; `--wait` ожидает её готовности. PostgreSQL также имеет собственный healthcheck `pg_isready`.

TSX обрабатывается встроенным компилятором Vite без Babel и `@vitejs/plugin-react`. При разработке изменение компонентов перезагружает страницу; React Fast Refresh не используется. Runtime-зависимости frontend — только React и React DOM. Пакеты Backend обеспечивают OpenAPI, Swagger UI, провайдер PostgreSQL и инструменты миграций EF Core; неиспользуемых прямых ссылок нет.

Состояние редактора описано типизированными вариантами: пустой редактор, загрузка, готовая к вводу заметка, сохранение и ошибки. Черновик хранится отдельно от последнего подтверждённого содержимого. Запрос списка выбирает только поля карточки и обрезает текст в PostgreSQL; полное содержимое загружается отдельным GET при выборе записи. Результат создания явно содержит признак новой записи для ответа `201` или `200` при повторе.

## REST API

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/notes` | Активные заметки, новые первыми. Параметры `notebookId`, `tagId` и `query` комбинируются. `trash=true` возвращает корзину |
| POST | `/api/notes` | Создание в блокноте `notebookId` или в «Личном» |
| GET | `/api/notes/{id}` | Полное содержимое выбранной заметки; `404`, если запись отсутствует |
| PUT | `/api/notes/{id}` | Сохранение заголовка и текста с задачами; возвращает полную заметку; `404`, если запись отсутствует |
| PATCH | `/api/notes/{id}/organization` | Перенос по `notebookId`, назначение тега по `tagId` или `tagName`, снятие по `removeTagId` |
| POST | `/api/notes/{id}/trash` и `/api/notes/{id}/restore` | Перемещение в корзину и восстановление |
| GET, POST | `/api/notebooks` | Список и создание блокнотов. Для создания передаётся `name` |
| GET | `/api/tags` | Список тегов |

Перенос, работа с тегами, удаление и восстановление передают актуальную `version` заметки.

Пример тела POST (для PUT добавьте поле `version` из последнего ответа API по заметке):

```json
{
  "title": "План на неделю",
  "content": "Завершить макет и записать идеи.\n\n- [ ] Проверить макет"
}
```

Для POST допустимо `{}`. Для PUT обязательна `version`, включая `0` для только что созданной заметки. При попытке записать отличающиеся данные поверх более новой версии API возвращает `409 Conflict`. Поле `content` содержит весь текст, включая строки задач вида `- [ ]` и `- [x]`. Продолжение многострочного пункта начинается с `  | `. API по-прежнему принимает старый массив `checklist` в запросе и добавляет его пункты в текст. В ответе задачи приходят в составе `content`. Поля `title` и `content` допускают `null`. POST возвращает `201 Created`. Необязательный заголовок `Idempotency-Key` принимает непустой UUID: повтор исходного запроса возвращает `200 OK` и текущую версию той же записи, в том числе после редактирования и перезапуска сервера. Для заметок из предыдущей версии в качестве исходных используются первые доступные данные после обновления базы. При повторе ключа с другими данными возвращается `409 Conflict`. Frontend использует этот ключ автоматически. Ошибки ввода — `400` в формате ValidationProblemDetails; неожиданные ошибки не раскрывают внутренние детали.

## Разработка без контейнеров

Требуются .NET SDK 10 и Node.js 22.12+. PostgreSQL можно оставить в контейнере. Если приложение уже запущено целиком через Compose, остановите его frontend/backend перед использованием тех же портов:

```sh
docker compose stop frontend backend
docker compose up -d --wait postgres
```

Терминал 1, из корня:

```sh
dotnet run --project backend --urls http://127.0.0.1:5080
```

Терминал 2:

```sh
cd frontend
npm ci
npm run dev
```

Приложение: http://127.0.0.1:5173. Vite проксирует `/api` к Backend. Строка подключения в `backend/appsettings.json` использует стандартные локальные параметры PostgreSQL. При изменении параметров в `.env` передайте соответствующую строку через переменную `ConnectionStrings__Notes` процессу `dotnet run`: `.env` автоматически читает Compose, а не .NET. Для изменения схемы:

```sh
dotnet tool restore
dotnet ef migrations add MigrationName --project backend --output-dir Infrastructure/Persistence/Migrations
```

В PowerShell с запрещённым выполнением `.ps1` для команд npm/npx можно использовать `npm.cmd` и `npx.cmd`.

## Проверки

Сборки:

```sh
dotnet build backend -c Release
cd frontend
npm ci
npm run build
npx playwright install chromium firefox
```

Из корня, PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Test.ps1
```

Скрипт запускает Chromium и Firefox в отдельном Compose-проекте с PostgreSQL и проверяет сохранность заметок после перезапуска и пересоздания контейнеров Backend и PostgreSQL. Нужны установленные npm-зависимости и браузеры Playwright.

Сценарии охватывают US-01–US-10, включая автосохранение, чек-листы, перенос между блокнотами, фильтрацию и поиск, удаление и восстановление. Для запуска против уже работающего приложения перейдите в `frontend` и выполните `npm run test:e2e`. Проверки создадут тестовые записи в его БД. При нестандартных портах задайте `E2E_BASE_URL` и `E2E_API_URL`.

Сопоставление с документами и границы реализации: [docs/requirements.md](docs/requirements.md). Результаты фактических проверок: [docs/verification.md](docs/verification.md).
